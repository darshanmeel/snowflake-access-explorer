## Logic and speed (access.py)

### 1. Can they?, Where to cut, Granted vs used and Role 'if revoked' walk every simple path: 33 s+ per call on the big test account
`access.py:1607` · perf · impact high

access_of() builds walk() x granted, which is every simple path times every grant. On test_access.big() access_of('BIG_01', True) returns 25,681,800 rows and takes 32.8 s (walk alone: 431k paths, 2.5 s). It is the base of can() (2905), removal() (2858), cut_points() (2948), loses() (2328) and losers() (2849). losers() calls access_of(v, True) once for every user behind each cut edge, and removal() calls losers() once per option. server.check_page (server.py:1370) calls can() once per held privilege, server.py:767 calls loses() once per unused role, and server.py:1105 calls it once per user who loses the role. can() also returns every path without a MAX_PATHS cap. All of this runs under the single server.LOCK (server.py:52), so one Can they? request on a big account blocks every other request. This breaks the CLAUDE.md rule 'exact path counts without listing, every chain listed lazily up to MAX_PATHS'.

**Fix:** Rewrite can(), removal(), cut_points() and loses() on top of fast() and listed(). Set holders = {r for r, pv, k in on[obj] if pv == priv}, take sts, kids, cnt, hops = fast(name, is_user), list paths = listed(sts, kids, hops, holders) (capped, plus capped_paths for the shortest), and get count = sum(cnt[h]). For choke points, count instead of listing: an edge is on every path when paths_through_edge == total, using counts from the start and counts up from the holders. Do losers() and loses() by reach: for each user in users_through(grantee), run a BFS from starts(u) that skips the cut edges (as what_if already does with paths_from) and test whether any holder is still reached. Cap the paths in the can() output at MAX_PATHS and add a count.

**Checker:** Confirmed. access_of() (access.py:1607) is walk() x granted with no cap. On big(), walk('BIG_01', True) gives 431,254 paths and access_of would produce 25,681,800 rows. can(), removal(), cut_points(), loses() and losers() all build on it, and can() returns every path uncapped. This conflicts with the CLAUDE.md rule 'every chain listed lazily up to MAX_PATHS'.

### 2. What changed: facts() runs grants() + access_objects() for every user, about 19 min per snapshot on big()
`access.py:3839` · perf · impact high

facts() builds access {(user, object): (level, privileges)} with access_objects(grants(u, True), True) for every user. Measured on big(): 10 users take 22.8 s, so the 500 users take about 19 minutes, and diff() needs it for the current snapshot and for the previous one (loaded()). The work runs under the server lock, so the What changed page and watched questions are unusable on a real account and block everyone else meanwhile.

**Fix:** facts only needs the highest level per data object, not paths. Cache per role: lv(r) = {object: (level, privileges)} over bfs([r]) (as data_use/own_use already do with priv classes). Per user, merge lv over best_paths(u, True).keys() (the roles reached). The 'admin' step is set when an ADMIN role is reached. That gives roles x objects work once, then users x reached roles, with no path listing.

**Checker:** Confirmed at access.py:3839: it runs access_objects(grants(u, True), True) for every user. Measured on big(): 10 users take 17.9 s, so 500 users take about 15 min. diff() (3914/3917) calls facts() for the current snapshot and the previous one.

### 3. access_objects() scans every listed path of every row for admin roles: 3.4 s for one user's Access page on big()
`access.py:1086` · perf · impact high

`any(n in ADMIN for r in rs for p in r['paths'] for n in p[1:-1])` and `routes = {tuple(p[:-1]) ...}` walk up to MAX_PATHS paths for each row of each object. In the nearest() profile this genexpr ran 73.7M times. access_objects(grants('BIG_01'), True) takes 3.4 s, more than grants() itself (1.5 s). It feeds the Access page (server.py:950), My access (server.py:1007), compare(), granted_used(), brings() and facts(). build() drops every role link whose grantee is an admin role, so an admin role holds no roles. It can therefore only be the last role on a path, the grant holder, which makes this scan equivalent to a check on the holders.

**Fix:** Replace the scan with `any(h in ADMIN for r in rs for h in r['holders'])`. Compute ways from max(r['count']) (or from the distinct path lists by id(), since grants() shares them between rows) instead of re-tupling every path. Add access_objects to test_perf.

**Checker:** Confirmed. access_objects(grants('BIG_01', True), True) took 2.5 s, more than grants() at 1.5 s. build() (access.py:887) drops role links whose grantee is an admin role, so an admin role holds no roles and can only be the grant holder on a path. The fix needs one tweak: p[1:-1] leaves out the start, so the holder check must also skip the subject. Otherwise an admin role's own Access page would get level 'admin'. Use `any(h in ADMIN and h != subject ...)` or compare against rs paths' p[0].

### 4. nearest() takes 39 s on big(): brings() runs full grants() + access_objects() for every candidate role

**Checker:** Confirmed. brings() (access.py:2986) runs grants(role) plus access_objects() just to count other objects. ### 6. Default role only: start paths include routes through other granted roles, so counts and depth are overstated

### 7. Up-walks (who_can, held, admin_holders, rule 19, rule 22, can().closest) list every simple path with no MAX_PATHS cap
`access.py:1639` · perf · impact medium

up() enumerates every simple path from a holder to every grantee. who_can() returns 17,016 rows for one table on big(). held() (2315) reports count=len(ps), a listing rather than a count, and sends every path. admin_holders() (1628), rule19 (4347, via up([h])), rule22 (via who_can), ask_for() (2888, who_can just to find functional roles) and can().closest (2920) all use it. **Fix:** Add an up-side twin of fast(): dag over held_by, counts by layer, shortest by reverse()/BFS, listed() capped at MAX_PATHS. Use it in who_can/held/grantees. rule19 and ask_for only need the shortest path per grantee, which reverse() already gives. can().closest needs only the shortest user-started chain: one BFS from the holders over held_by plus users_of.

**Checker:** Confirmed. up() (access.py:1281) enumerates every simple path with no cap. who_can('DB0.S0.TBL_00') returns 17,016 rows on big(), though fast here (0.06 s). held() sets count=len(ps) from the listing and keeps every path. admin_holders(), ask_for() and can().closest use up() directly. The exponential risk on deep diamond-shaped hierarchies is real, even though the test data stays fast.

### 10. dag() drops loop-closing links in traversal order, so counts and shortest paths disagree with can() when the role graph has a cycle
`access.py:1374` · bug · impact low

Back edges are removed relative to the depth-first order. For roles A->B, A->C, B->C, C->B with SELECT on B (user U -> A), grants('U', True) reports count 1 (U > A > B), while can() via down() lists 2 paths (U > A > B, U > A > C > B). reach() also gives B count 1 and C count 2, so the result depends on holds order. Snowflake rejects cyclic role grants, but a SHOW-fallback snapshot read with 16 parallel threads during an IaC apply, or a later what_if, can contain one. The 'exact counts' then silently differ between pages.

**Fix:** Detect cycles once in build(): run Tarjan SCC over holds, record roles in a non-trivial SCC in memo, and show the same warning the UI shows for capped ('role loop between X, Y: counts are approximate'). Alternatively, have count paths fall back to the enumerating walk only inside SCCs. Add the 4-role cycle to test_access so both sides are pinned.

**Checker:** Reproduced with roles A->B, A->C, B->C, C->B and SELECT on B. grants('U', True) gives count 1 (U > A > B), while can() lists 2 paths (adding U > A > C > B). Impact is low because Snowflake rejects cyclic role grants, but the inconsistency is real for snapshots that contain a loop.
