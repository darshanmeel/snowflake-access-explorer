Two front ends share one API and one logic file; only SP_ACCESS_SNAPSHOT (sql/1_setup.sql) writes to Snowflake.

  • The app is read-only: no GRANT, REVOKE or DDL (CLAUDE.md "Hard rules").
  • The only write is the procedure, called by the Rebuild button (server.py:2134; test_server.py:322).
  • access.py holds all data logic; server.py and app.py have none of their own (server.py:1-4; CLAUDE.md "Two versions").
  • Local web version is the default; Streamlit in Snowflake runs the same React app (app.py:9-20; st_react.py:51-75).
  • Data needs no real-time freshness: the UI shows "Data from <time>" (CLAUDE.md).
  • Three shared-data sources: fake, direct, objects (cache.config, cache.py:27-40).

  • snapshot() reads only the newest OK run; a half-finished run is never shown (access.py:403-406).
  • Missing OBJECT_USE or ACTIVITY (older setup) gives None, not an error (access.py:58-59, 411-415).
  • Busy check: each CALL inserts its RUNNING row first, then only the earliest RUNNING run of the last hour goes on; a second CALL deletes its own row and returns SKIPPED (sql/1_setup.sql:510-524).
  • A FAILED run deletes its own rows; an OK run deletes older runs' rows, but never the rows of a run still RUNNING (under a day old) (sql/1_setup.sql:547-560).
  • Per-source failures keep the run OK: a refused usage or activity read gives that source UNAVAILABLE with a note; a refused SHOW FUTURE GRANTS skips only that schema or database (one note per database); in the SHOW fallback a role whose SHOW GRANTS TO or OF is refused is skipped whole, listed in NOTES (sql/1_setup.sql:224-236, 279-293, 333-340).
  • Step activity() of the procedure reads ACCESS_HISTORY with QUERY_HISTORY (role, statement type) and SESSIONS (client) for ACTIVITY_DAYS (60), aggregated per UTC day, user, role, client, object, Streamlit app, action and statement type, with the queries per UTC hour (HOURS); never query text (sql/1_setup.sql:540-590).
  • Off-hours are not stored: access.activity() splits HOURS into weekday and weekend hours (the weekend is the UTC day), and the page counts the hours outside WORK_HOURS (default 7-19, local, Monday to Friday) after shifting them from UTC by the business-time slider (UTC-12 to UTC+14) on the Activity tab (access.py:4289-4340; server.py:1656-1692). Older snapshots without HOURS give no off-hours.
  • The Activity tab is one log of stacked sections with Change object and the business-time slider at the top. A table, view or app shows the one-object sections (tiles, queries by client, statement kinds, role-by-client grid, queries by statement type and per day, who used it, sensitive columns, grant paths, DDL changes, copy-only query SQL, checks); a database, schema, person or role adds off-hours by people, who touched what, hours of use and objects busiest first. It follows the object type: table or view; Streamlit app (queries it ran for its viewers, matched on APP; who opened it, can open, never did; saw data they cannot read; opened without access now); database or schema (every object in it); warehouse (QUERY_HISTORY: who ran queries on it, who can use it and did not; no ACCESS_HISTORY rows); person; role (server.py:1656-1692). Opening an app without a table query leaves no row.
  • It copies the days the last OK run has up to the day before its last day, and reads from that day on, because ACCESS_HISTORY lags up to 3 hours (access.activity_start). There is no fallback: without Enterprise edition the source is UNAVAILABLE and the Activity tabs and rules 24-28 say why.
  • "Read Snowflake again" = {what:"page"}: drop the cache only, the next page reads again (server.py:2149-2152).
  • Fake mode never CALLs (server.py:2126-2145).

14.8 Limits

  • No future grants: they are not in ACCOUNT_USAGE.
  • SHOW FUTURE GRANTS IN SCHEMA ... lists them; the app's snapshot reads them.
  • 5_object_users.sql counts only grants on that exact object.
  • Grants on its schema or database are not followed: ask for DB.SCHEMA or DB separately.
  • Shows granted access, not masking or row access policies.
  • Cost grows with the number of role paths, not with privileges.
  • Lower MAX_DEPTH is faster but drops deeper rows.
  • Untested on a real account: the tests run on DuckDB.
  • Not proved: table functions (recursive CTE in a UDTF), ACCOUNT_USAGE inside a function.
  • The rules exist twice (SQL here, access.py in the app).
  • Only test_queries.py keeps them equal.
