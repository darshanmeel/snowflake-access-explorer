sql · correctness / idempotency of the snapshotsql/1_setup.sql:501-506, 537-539

Problem. The busy check only counts RUNNING rows started in the last hour, and it is not atomic (a SELECT followed by an INSERT). When a run succeeds it deletes every row whose RUN_ID <> its own, including the rows of another run that is still RUNNING.

Why. Two overlapping CALLs leave the newest OK run with missing datasets, and the app reads it as a complete snapshot. It shows fewer grants, users or roles and no error. Overlaps are realistic: the SHOW fallback is sequential (2 SHOWs per role, plus a SHOW FUTURE GRANTS per schema), so it can pass 1 hour on accounts with thousands of roles. Also, any app user can press Refresh, and two clicks a few milliseconds apart both pass the check.

Scenario. Run A (P_SOURCE=SHOW, 4000 roles) starts at 07:00. At 08:05 a user clicks Refresh: run B starts because A started more than 1 hour ago, and B writes its GRANT and USER_ROLE rows. At 08:10 A finishes OK and runs DELETE ... WHERE RUN_ID <> A, which removes B's grant rows. B goes on with users, tags and the rest, ends OK with ROW_COUNTS.grants = 0, and deletes A's rows. The app now loads B (latest FINISHED_AT) with no grants at all.

Fix. On OK, delete only the rows of runs that started before this one and are not still running. For example: DELETE FROM t WHERE RUN_ID IN (SELECT RUN_ID FROM RUN WHERE STARTED_AT < (SELECT STARTED_AT FROM RUN WHERE RUN_ID = :this) AND (STATUS <> 'RUNNING' OR STARTED_AT < DATEADD(DAY, -1, CURRENT_TIMESTAMP()))). Add a test_sql test that runs two overlapping runs through fake_session.

Verified: Confirmed in run(): busy check is a non-atomic SELECT then INSERT, limited to RUNNING rows from the last hour, and on OK it runs DELETE ... WHERE RUN_ID <> this for every DATA table, which also removes a run that is still RUNNING. server.LOAD only serialises calls inside one process; a daily task and an app click, or two SiS sessions, can overlap. snapshot() then takes the newest OK run by FINISHED_AT, which may be a run whose rows were deleted. The data loss is silent but needs an overlap.
